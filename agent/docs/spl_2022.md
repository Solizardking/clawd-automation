# SPL Token-2022 Swap Design

This page documents the end-to-end design for safely swapping **Token-2022**
mints (and legacy SPL tokens) through the kit. It covers the threat model,
the safety check that runs before a swap, the authenticated Jupiter client,
and how the pieces are wired into the agent.

## Why Token-2022 changes the risk profile

The legacy SPL-Token program has a fixed account layout. Token-2022 replaced
that with a variable-length **TLV** (Type-Length-Value) format so mints can
carry optional **extensions**. Some extensions materially change transfer
semantics and create rug/exit vectors that a standard SPL mint cannot express:

| Extension | What it does | Why it matters for a swap |
|---|---|---|
| `PermanentDelegate` | A delegate that can transfer **or burn** tokens from every holder, forever | A malicious mint can sweep your purchased tokens after you buy |
| `TransferFeeConfig` | A per-transfer fee (a "tax token") with a withheld-fee authority | Every swap is taxed; the authority can withdraw accumulated fees |
| `TransferHook` | Every transfer CPI-invokes an arbitrary program | The hook program can gate/block sells (common on post-migration Pump.fun tokens) |
| `FreezeAuthority` (base) | An authority that can freeze any token account | Holders can be locked out of their balance |
| `DefaultAccountState = Frozen` | New accounts initialize as frozen | Incoming tokens are unusable until unfrozen |
| `MintCloseAuthority` | An authority can close the mint | Remaining supply (including **your** balance) can be destroyed |
| `InterestBearingConfig` | Balances re-base over time at a configurable rate | Your balance drifts while held |

## Design overview

```text
instruction ("buy 0.05 SOL of <mint>")
        │
        ▼
┌───────────────────────────────┐
│ ReasoningLoop (rig agent)     │
│   • calls CheckTokenSafetyTool │
└───────────────┬───────────────┘
                ▼
┌───────────────────────────────┐
│ check_token_safety(rpc, mint) │
│   • read mint account once    │
│   • identify Token-2022       │
│   • unpack TLV extensions     │
│   • return TokenSafetyReport  │
└───────────────┬───────────────┘
                ▼  (if safe, or after review)
┌───────────────────────────────┐
│ PerformJupiterSwap            │
│   • fetch_quote → api.jup.ag  │
│     (x-api-key when set)      │
│   • swap-instructions → tx    │
│   • sign & send via signer    │
└───────────────────────────────┘
```

## 1. Safety check — `check_token_safety`

**Module:** [`src/solana/safety.rs`](../src/solana/safety.rs)

The check is **read-only** — it never constructs transactions or signs. It
fetches the mint account once and returns a structured
`TokenSafetyReport`:

```rust
pub struct TokenSafetyReport {
    pub mint: String,
    pub program: String,          // SPL Token or Token-2022 program id
    pub is_token_2022: bool,
    pub freeze_authority: Option<String>,
    pub mint_authority: Option<String>,
    pub risky_extensions: Vec<RiskyExtension>,
    pub safe: bool,               // true when no risky extensions found
}

pub struct RiskyExtension {
    pub name: &'static str,       // PermanentDelegate | TransferFee | TransferHook | ...
    pub detail: String,           // human-readable why-it's-risky + key addresses
}
```

### Legacy SPL mint path

When the mint account owner is the legacy `Tokenkeg...` program, there are no
TLV extensions. Only the base authorities are inspected:

- `mint_authority` (COption<Pubkey> @ offset 0) — non-null means supply can
  still be minted.
- `freeze_authority` (COption<Pubkey> @ offset 45) — non-null means any holder
  account can be frozen.

A freezable legacy mint is flagged in `risky_extensions`.

### Token-2022 mint path

When the owner is `TokenzQdBNbLqP5VEhdkAS6EPFLC1PHnBqCXEpPxuEb`, the account
data is unpacked via the crate's zero-copy `PodStateWithExtensions::<PodMint>`
API:

```rust
use spl_token_2022::extension::{
    BaseStateWithExtensions, ExtensionType, PodStateWithExtensions,
};
use spl_token_2022::pod::PodMint;

let state = PodStateWithExtensions::<PodMint>::unpack(&account.data)?;
let extension_types = state.get_extension_types()?;
```

For each risky extension present, the check unpacks the extension payload
(`PermanentDelegate`, `TransferFeeConfig`, `TransferHook`,
`InterestBearingConfig`, `DefaultAccountState`) and extracts the addresses /
fees / rates relevant to the decision.

## 2. Authenticated Jupiter client — `Jupiter`

**Module:** [`src/solana/jup.rs`](../src/solana/jup.rs)

Jupiter's paid tier is served from `api.jup.ag` and authenticates with an
`x-api-key` header on every request. The free tier is `quote-api.jup.ag` and
requires no key.

```rust
fn base_url() -> &'static str {
    let key = std::env::var("JUPITER_API_KEY").unwrap_or_default();
    if key.trim().is_empty() {
        "https://quote-api.jup.ag"   // free / unauthenticated
    } else {
        "https://api.jup.ag"         // paid tier, x-api-key attached
    }
}
```

When `JUPITER_API_KEY` is set, all quote and swap-instruction requests go to
`api.jup.ag` with the `x-api-key` header, unlocking higher rate limits and
priority routing. When unset, the kit silently falls back to the free
endpoint — no behavior break.

## 3. Agent wiring

The safety tool is attached to every Solana agent in
[`create_solana_agent`](../src/solana/agent.rs):

```rust
.tool(PerformJupiterSwap)
.tool(CheckTokenSafetyTool)   // inspect mint extensions before trading
.tool(TransferSol)
// ...
```

`CheckTokenSafetyTool` exposes the Rust check as a rig `#[tool]` so the model
can call it for any mint. The tool description tells the model to ALWAYS call
it before a swap/transfer unless the token is a known blue-chip (SOL, USDC,
USDT, JitoSOL, …).

## 4. End-to-end flow (ooda / agent bridge)

The ooda harness reaches the kit through the server-to-server
[`/agent/act`](http_service.md) bridge (`agent/src/http/agent_bridge.rs`):

1. ooda's `web/agent-kit.ts` forwards
   `{ instruction: "buy 0.05 SOL of <mint>" }` with the shared
   `X-Agent-Key` secret.
2. The kit builds `create_solana_agent(...)`, which includes
   `CheckTokenSafetyTool`.
3. The reasoning loop lets the model call the safety tool, inspect the JSON
   report, and (if safe) call `PerformJupiterSwap` with the authenticated
   Jupiter client.
4. The swap transaction is signed by the kit's configured signer
   (`SOLANA_PRIVATE_KEY` for the local signer) and returned/sent.

Both `BIRDEYE_API_KEY` (liquidity/holder screening) and `JUPITER_API_KEY`
(tiered routing) are wired into the kit's env template and forwarded by the
ooda deployment docs (see `ooda/README.md`).

## Env vars

| Variable | Purpose |
|---|---|
| `JUPITER_API_KEY` | Authenticated `api.jup.ag` swaps; fallback to free tier when unset |
| `HELIUS_RPC_URL` | Helius RPC with `?api-key=`; overrides `SOLANA_RPC_URL` when set |
| `HELIUS_API_KEY` | Helius DAS/metadata (Token-2022-aware metadata) |
| `BIRDEYE_API_KEY` | Market data / liquidity screening for pre-swap checks |
